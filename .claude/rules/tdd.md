# TDD Rule

> **경고: 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 프로젝트 규칙 우선 조항

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 관련 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수 대상

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리, 외부 호출 래퍼)
- **유틸 / 순수 함수**
- **버그 수정** (재현 테스트를 먼저 작성해 실패를 확인한 뒤 수정)

### TDD 불필요 대상

- **타입 정의** (`type`, `interface`)
- **설정 파일** (vite/eslint/tsconfig 등)
- **순수 UI** (로직 없는 마크업, 스타일)
- **SQL** (스키마, 마이그레이션, 쿼리 파일)

판단이 애매하면 **로직이 있으면 필수**로 간주한다.

## RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트**. 한 테스트에 여러 동작을 담지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류, 잘못된 셋업으로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 분기, 옵션, 일반화는 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 실행해서 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 수행한다.
- **green을 유지**한다. 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 간다.

### 반복

- REFACTOR가 끝나면 **다음 동작에 대한 RED로 돌아간다.** 모든 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.
- 삭제는 협상 대상이 아니다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순한 코드가 가장 자주 조용히 깨진다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현을 그대로 따라 쓰게 되어 버그를 잡지 못한다. 실패를 본 적 없는 테스트는 검증이 아니다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. TDD는 시간을 아끼는 경로다. |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 곧 프로덕션이 된다. 버릴 코드라면 삭제 비용도 없다. |
