# Commit

변경사항을 분석해 컨벤션에 맞는 커밋으로 정리한다. 사용자 승인을 따로 받지 않고 바로 커밋한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

- `git status --short` — 변경·추가·삭제된 파일 목록
- `git diff` — 아직 stage되지 않은 변경
- `git diff --staged` — 이미 stage된 변경
- `git log --oneline -10` — 기존 커밋 메시지 스타일 확인

변경이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 끝낸다.
git 저장소가 아니면 그 사실을 알리고 `git init`을 할지 사용자에게 묻는다.

diff는 파일 목록만 보지 말고 실제 내용을 읽어 변경의 의도를 파악한다.

### 2. 논리적 단위로 분류

하나의 커밋은 하나의 목적만 갖는다. 다음 기준으로 나눈다.

- 기능 추가, 버그 수정, 리팩터링, 설정·의존성 변경은 서로 다른 커밋으로 분리한다.
- 같은 목적에 속한 파일(예: 컴포넌트와 그 테스트, 스타일)은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p` 대신 사용자에게 분리 여부를 묻는다.
- `.env`, 키·토큰이 들어간 파일, `node_modules`, 빌드 산출물(`dist` 등)은 stage하지 않고, 발견하면 사용자에게 알린다.

변경이 하나의 목적뿐이면 커밋 1개로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

- type은 아래 중 하나를 쓴다.
  - `feat`: 새 기능, 사용자에게 보이는 UI 변경
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 구조 개선
  - `chore`: 설정, 의존성, 빌드, 문서 등 그 외
- 요약은 한국어로, 50자 안팎의 현재형 문장으로 쓰고 마침표를 붙이지 않는다. 무엇을 했는지가 드러나야 한다.
- 이유나 맥락이 diff만으로 드러나지 않을 때만 본문을 추가한다. 본문은 "왜"를 설명한다.
- `git log`에서 확인한 기존 스타일이 이 형식과 다르면 사용자에게 어느 쪽을 따를지 묻는다.
- 메시지 끝에 한 줄을 띄우고 공동 작성자 트레일러를 붙인다.

```
Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

좋은 예:
- `feat: 프롬프트 입력창에 예시 선택 기능 추가`
- `fix: API 키가 없을 때 생성 요청이 두 번 전송되는 문제 수정`
- `refactor: 컴포넌트 카드의 탭 상태 로직 분리`
- `chore: galmuri 폰트 의존성 추가`

나쁜 예: `fix: 수정`, `feat: 여러 가지 변경`, `update files`

### 4. 바로 커밋

승인을 기다리지 않고 분류한 커밋 단위마다 다음을 순서대로 실행한다.

1. `git add <파일들>` — `git add -A`나 `git add .`는 쓰지 않고 파일을 명시한다.
2. `git commit -m "<메시지>"` — 여러 줄 메시지는 heredoc으로 전달한다.
3. 마지막에 `git log --oneline -5`와 `git status --short`로 결과를 보고한다. 커밋별 메시지, 포함 파일, stage하지 않고 제외한 파일과 그 이유를 함께 알린다.

## 규칙

- 커밋 전에 사용자 승인을 받지 않는다. (푸시·PR 등 외부 공개 동작에는 이 규칙이 적용되지 않는다.)
- 푸시(`git push`)는 하지 않는다. 사용자가 따로 요청할 때만 한다.
- `--no-verify`, `--amend`, `reset --hard` 같은 우회·파괴적 옵션은 사용자가 요청하지 않는 한 쓰지 않는다.
- pre-commit 훅이 실패하면 원인을 고치고 새 커밋으로 다시 시도한다.
